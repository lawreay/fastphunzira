# Certificate Specification

## 1. Purpose

Certificates provide proof that a learner successfully completed a course or assessment. FastPhunzira must issue certificates consistently, protect them from fraud, and make them publicly verifiable without exposing sensitive learner data.

## 2. Certificate Workflow

```text
Student meets course/exam requirements
   ↓
Eligibility is checked server-side
   ↓
Certificate is generated
   ↓
Certificate number and verification code are assigned
   ↓
PDF or HTML certificate is stored
   ↓
Certificate is made available to student
   ↓
Public verification checks the certificate record
```

## 3. Certificate Eligibility

A certificate should only be issued when all relevant rules pass, such as:
* course enrollment is valid
* required lessons are completed
* passing exam requirement is met
* no active violations or restrictions exist
* certificate generation conditions are satisfied

## 4. Certificate Number Format

Recommended format:

```text
FP-2026-000001
```

Rules:
* unique across all issued certificates
* generated by the server
* stored permanently with the certificate record
* not derived from a user ID or other insecure value

## 5. Verification Model

Each certificate should include:
* certificate number
* verification code
* issued date
* course name
* learner name
* score or result summary
* certificate status

The verification flow should check both the certificate number and verification code before returning public result data.

## 6. Public Verification Access

Public verification route:

```text
/verify/{certificate_number}
```

Example:
```text
/verify/FP-2026-000001
```

The system should return a brief success or not found result without exposing private account data beyond the approved public certificate fields.

## 7. Certificate Storage

The system should preserve:
* generated file location
* verification code
* issue date
* linked user and course metadata
* status and revocation state if applicable

## 8. PDF or File Output

The certificate record may be produced as:
* PDF file
* HTML-rendered certificate
* downloadable certificate preview

The file should include:
* institution or platform name
* learner name
* issued course or program name
* completion date
* approval or signature metadata where applicable

## 9. Revocation and Reissuance

The platform should support:
* certificate status values such as active, revoked, expired, or invalid
* revocation by admin when required
* reissue rules when a certificate is invalid or needs correction

## 10. Security Considerations

* Verification codes must be generated securely
* Do not expose internal database identifiers
* Never allow certificate lookup to reveal student private information
* All certificate generation should happen on the server
* Reject tampered or forged certificate requests at the application layer

## 11. Example Response

```json
{
  "success": true,
  "data": {
    "certificate_number": "FP-2026-000001",
    "student_name": "Jane Doe",
    "course_name": "Business Ethics",
    "score": 88,
    "issued_at": "2026-09-23",
    "status": "active"
  }
}
```

## 12. Implementation Notes

Certificate issuance should be treated as a business-critical event. The platform should keep an auditable record of every generated certificate and ensure verification remains stable, secure, and easy to use.
